# Canonical Solve Notes

## 1. Problem
`SqliteClient.db_delete()` calls `os.remove(self.filename)` when tearing down/deleting an in-memory SQLite database configured via `sqlite://:memory:`. On Windows, attempting to remove the special filename `:memory:` (or similar reserved/invalid path syntax) does not raise `FileNotFoundError` as it would on POSIX systems; instead the OS raises `OSError: [WinError 123] The filename, directory name, or volume label syntax is incorrect`, which propagates uncaught and breaks teardown/cleanup flows (e.g. test finalizers, `Tortoise.close_connections()`/db cleanup) exclusively on Windows. The root cause is that the existing exception handling in `db_delete` only anticipates `FileNotFoundError` and does not account for platform-specific `OSError` variants (errno 22 / invalid argument) that Windows raises for this pseudo-filename.

## 2. Load-bearing changes
- `tortoise/backends/sqlite/client.py`, `SqliteClient.db_delete`: add an `except OSError as e` clause after the existing `except FileNotFoundError` clause; if `e.errno != 22` re-raise, otherwise swallow it. This specifically absorbs the Windows-only invalid-filename error for `:memory:` while still propagating genuine OS errors (e.g. permission denied) unchanged. This is the actual fix for the reported bug.
- `tortoise/__init__.py`: version bump to `0.16.11` — packaging/release bookkeeping, not functionally load-bearing for the bug fix.
- `CHANGELOG.rst`, `CONTRIBUTORS.rst`: documentation/release notes — not functionally load-bearing.
- The remaining changes in the fix patch (`ExistsQuery`/`exists()` in `queryset.py` and `models.py`, `Model.__getitem__`/`_getbypk` in `models.py`, `execute_bulk_insert` custom-PK handling in `backends/base/executor.py`, `docs/examples/fastapi.rst` literalinclude, new `examples/fastapi/_tests.py`) are unrelated feature additions bundled into the same release and are not required to resolve the Windows `:memory:` OSError issue; they address separate issues (`bulk_create` id ordering, `exists()` API, FastAPI example tests) tracked alongside this one.

## 3. Correct verification behavior
- Since the underlying `WinError 123` only reproduces on Windows, verification on a non-Windows CI environment must rely on code inspection and a targeted reproduction: construct a `SqliteClient` (or use `Tortoise.init` with `db_url="sqlite://:memory:"`), then call `db_delete()` (directly or via the normal teardown path such as `Tortoise.close_connections()` / test `finalizer()`), and confirm no unhandled exception propagates.
- Confirm the `except OSError` branch is scoped to only swallow `errno == 22` and still re-raises other `OSError`s — this can be checked by simulating an `OSError` with a different errno (e.g. monkeypatching `os.remove` to raise `OSError(13, "permission denied")`) and asserting it still propagates, while an `OSError(22, ...)` is suppressed.
- Confirm that in-memory database usage (`sqlite://:memory:`) continues to work end-to-end (connect, run migrations/queries, close) on the platforms available in CI, ensuring no regression to normal sqlite file-based deletion behavior (`FileNotFoundError` still handled, real files still removed).
- Run the sqlite backend tests (e.g. anything exercising `Tortoise.init`/`close_connections`/test `initializer`/`finalizer` with the sqlite in-memory URL) to ensure teardown does not raise.

## 4. Traps and near-misses
- Catching only `FileNotFoundError` and ignoring the Windows-specific `OSError` entirely (i.e., leaving the original code unchanged) fails to fix the reported bug since Windows raises `OSError` with errno 22, not `FileNotFoundError`.
- Blanket `except OSError: pass` without checking `errno` would silently swallow legitimate OS errors (e.g., permission denied, disk errors) during real file deletion, masking genuine failures — the errno 22 check is required to keep the fix narrowly scoped.
- Checking `e.winerror == 123` instead of `e.errno == 22` would be Windows-only and fail on other platforms/interpreters where the attribute doesn't exist or the errno differs; the errno-based check is the portable, correct approach used in the fix.
- Attempting to special-case the `:memory:` filename by string-matching before calling `os.remove` (skipping the removal call entirely for `:memory:`) is a plausible alternative but changes behavior/flow more than necessary and isn't what the actual fix does; it also wouldn't generalize to other invalid-path scenarios that raise the same errno.
- Placing the new `except OSError` clause before `except FileNotFoundError` would break the `FileNotFoundError` handling on POSIX systems, since `FileNotFoundError` is a subclass of `OSError` and would be caught by the broader clause first if ordered incorrectly.
