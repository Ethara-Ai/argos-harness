# Canonical Solve Notes

## 1. Problem
Tortoise ORM had no declarative way to build SQL `CASE WHEN ... THEN ... ELSE ... END` expressions in `annotate()`/`filter()`. Users had to fall back to `RawSQL`, which is unsafe, unreadable and doesn't compose with Q-object filtering semantics. The observable symptom is the absence of `Case`/`When` classes in `tortoise.expressions`; attempting `Case(When(...), default=...)` raises `ImportError`. The root cause is architectural: `Q` lived in `tortoise/query_utils.py` and `Function`/`Aggregate` lived in `tortoise/functions.py`, each module unaware of the other, so there was no shared place to implement a `Case`/`When` expression that needs both Q-based condition resolution and Function-style field resolution.

## 2. Load-bearing changes
- `tortoise/expressions.py`: Moved `Q` here from `tortoise/query_utils.py` (now the canonical location), and moved `Function`/`Aggregate` here from `tortoise/functions.py`. This consolidation is required so that `When`/`Case` can use both `Q.resolve()` and `Function.resolve()`/`F.resolver_arithmetic_expression()` without circular imports.
- `tortoise/expressions.py`: Added `Expression` base class, `When(*args: Q, then=..., negate=False, **kwargs)` and `Case(*args: When, default=...)`. `When.resolve()` turns its Q objects/kwargs into a `WHERE`-style criterion and resolves `then` (supports plain values, `F`, arithmetic expressions, and `Function`/aggregate results) into a pypika term. `Case.resolve()` builds a pypika `Case()` chaining `.when(criterion, term)` for each `When` and `.else_()` for the default — this is the actual feature.
- `tortoise/query_utils.py`: `Q` class and `_process_filter_kwarg` removed (moved to expressions.py); `QueryModifier`, `Prefetch`, and `_get_joins_for_related_field` remain. `Q.resolve()` signature changed from `resolve(model, annotations, custom_filters, table)` to `resolve(model, table)`, with `_annotations`/`_custom_filters` now set as attributes on the Q/node before calling resolve (required because `Function`/`Case` need to inject annotations without changing every call site's signature).
- `tortoise/queryset.py`: `resolve_filters()` and other Q-consumers updated to set `node._annotations` / `node._custom_filters` before calling `node.resolve(model, table)` — mechanical follow-through of the Q API change, load-bearing because it's what actually wires new-style Q resolution into query building.
- `tortoise/functions.py`: Reduced to a thin module of concrete pypika-function wrappers (`Coalesce`, `Count`, etc.) that import `Function`/`Aggregate` from `tortoise.expressions`. Backward-compat re-export.
- `tortoise/models.py`, `examples/*.py`, docs: imports of `Q` updated from `tortoise.query_utils` to `tortoise.expressions` (compat shim likely still exists but canonical import moved).
- Everything else in the diff (bulk_create/ignore_conflicts, UUID pk bulk_update fix, mutable default fix, mysql/postgres/sqlite Rand functions, CI/tooling/asynctest removal, changelog/docs) are unrelated feature/bugfix bundles shipped in the same release and are not required to implement Case/When; they should not be treated as necessary for validating this specific feature.

## 3. Correct verification behavior
- Confirm `from tortoise.expressions import Case, When, Q, F` works and that `Case`/`When` are documented in `docs/expressions.rst`.
- Build a `Case(When(cond, then=val), When(...), default=...)` annotation via `Model.all().annotate(x=Case(...)).values(...)` and inspect `.sql()` output: verify correct `CASE WHEN <criterion> THEN <value> ... ELSE <default> END` syntax, correctly quoted per-dialect (sqlite/postgres double-quote vs mysql backtick identifiers), and correct literal quoting for string values.
- Verify condition inputs work both as keyword filters (`When(intnum__gte=8, then=...)`) and as `Q` objects (`When(Q(a=1, b=2), then=...)`), including negation (`negate=True`).
- Verify `then=`/`default=` accept plain values, `F()` field references, arithmetic expressions (`F("x") + 1`), and nested `Function`/aggregate calls (e.g. `Coalesce`), each producing correct SQL fragments.
- Verify a `Case` annotation can be used in a subsequent `.filter(annotated_field__in=[...])` — i.e., the annotation participates correctly in WHERE clause generation, not just SELECT.
- Run the full existing Q-resolution test suite (`tests/test_q.py`) with the new `q.resolve(Model, table)` two-argument signature (no more `annotations`/`custom_filters` positional args) to ensure the API change didn't break AND/OR/NOT/nested-Q semantics.
- Run `tests/test_aggregation.py`, `tests/test_filtering.py`, `tests/test_source_field.py` to confirm `Q` still imports/functions correctly from its new home (`tortoise.expressions`) and that annotate/filter combined with Function-based aggregates still produce correct SQL across sqlite/mysql/postgres.

## 4. Traps and near-misses
- Implementing `Case`/`When` as a standalone module without moving `Q` into `expressions.py` leads to circular imports (`When` needs `Q.resolve()`, `Q` conceptually belongs with filtering, `Function` needs to live where `Case` can use it for `then`/`default`) — a fix that just adds a new file importing from both `query_utils` and `functions` risks circular import errors or forces awkward local imports.
- Keeping `Q.resolve()`'s old 4-argument signature (`model, annotations, custom_filters, table`) while adding `Case`/`When` is a near-miss: `When` needs to resolve arbitrary nested `Q` objects for its condition without necessarily having `annotations`/`custom_filters` context threaded through, so the change to attribute-based (`node._annotations`, `node._custom_filters`) passing is necessary; a patch that keeps the old signature but bolts on `Case` will break wherever `Case`'s `When` needs to internally construct fresh `Q` objects without full annotation context, or will require passing empty dicts inconsistently and silently produce broken custom-filter/annotation resolution in nested cases.
- Building `Case`'s SQL by manually string-formatting `CASE WHEN ... THEN ... END` instead of using pypika's `Case()` builder is a plausible but fragile near-miss: it would fail to properly quote identifiers/literals per-dialect and wouldn't integrate with WHERE-clause criterion combination (needed for the `filter(annotated__in=...)` case).
- Treating `then=`/`default=` as accepting only literal values (ignoring `F`, arithmetic expressions, and `Function` objects) is a very plausible partial fix — it passes simple demos but fails on the documented use cases of computing derived values from other fields or wrapping aggregates.
- Not supporting `Q` objects as positional args to `When` (only kwargs) is a partial fix — the PR explicitly requires condition to accept "Q object or keyword filter, like input in Model.filter()".
- Assuming `bulk_create`/`UUID bulk_update`/`Rand` functions/mutable-default fixes are required for this feature — they are bundled in the same release but are independent issues; a solution that only implements those without Case/When does not resolve this PR, and vice versa a solution implementing Case/When without touching those areas is complete for this specific issue.
- Only adding `Case`/`When` to `tortoise/expressions.py` but leaving `Q` in `query_utils.py` with the old signature makes `When.resolve()` unable to reuse `Q`'s resolution logic cleanly without duplicating filter-parsing code (`_process_filter_kwarg`, `_resolve_nested_filter`, etc.) — duplicating this logic instead of relocating `Q` is a maintenance/correctness trap since it will drift from `Model.filter()`/`exclude()` semantics over time.
