# Canonical Solve Notes

## 1. Problem
`QuerySet.update()` and `Model.save()` only supported plain values and pypika `ArithmeticExpression` (i.e. `F` expressions) when generating UPDATE SQL. If a user assigned a custom pypika `Function` (e.g. `JSON_SET(...)`) to a model field and then called `save()`/`update()`, the executor tried to bind it as a normal parameterized value instead of inlining it as a SQL expression, so custom functions could not be used to update fields in place (the motivating use case being partial JSON field updates as raised in issue #537, and generally any DB-side function-based update). The root cause is in `tortoise/backends/base/executor.py`: `execute_update`/`get_update_sql` special-cased only `ArithmeticExpression` instances and ignored `pypika.terms.Function` instances.

## 2. Load-bearing changes
- `tortoise/backends/base/executor.py` (`BaseExecutor.execute_update`, `BaseExecutor.get_update_sql`):
  - Renamed/broadened the `arithmetic` dict to `arithmetic_or_function` and changed the isinstance check from `isinstance(instance_field, ArithmeticExpression)` to `isinstance(instance_field, (ArithmeticExpression, Function))`, importing `Function` from `pypika.terms`.
  - This is the core fix: any field value that is a pypika `Function` (which includes custom user-defined function subclasses such as a `JsonSet(Function)`), like `F` expressions before it, is now set directly into the `UPDATE ... SET` clause via `query.set(db_column, value)` instead of being passed as a bound parameter, allowing arbitrary custom SQL functions to be used for updates in both `Model.save(update_fields=...)` and `QuerySet.update(...)`.
- `tortoise/models.py` (`Model.refresh_from_db`, new method): Adds a way to reload field values (including ones set via `F`/`Function` expressions) from the database after a save, since those expression objects are not resolved client-side. This is a necessary companion feature for using `F`/custom-function updates on model instances (otherwise the in-memory attribute keeps holding the unresolved expression object instead of the new value) — directly resolves the "F Expression directly on object causing weird behaviour" issue bundled into this PR.
- `docs/functions.rst` and `docs/expressions.rst`: Documentation-only additions showing how to use a custom `pypika.terms.Function` subclass (e.g. `JsonSet`) with `.save()` and `QuerySet.update()`, and moving/expanding the F-expression docs to mention `refresh_from_db`. Not functionally load-bearing but describes the intended usage pattern.
- Everything else in the diff (timezone support via `tortoise/timezone.py`, `Tortoise.init` `use_tz`/`timezone` params, `DatetimeField` awareness changes, MySQL client timezone session var, `escape_datetime` isoformat change, CI/poetry/packaging migration, import-order/black reformatting, unrelated docstring/typo fixes) is unrelated infrastructure/feature work bundled in the same release patch and is not required to fix the "support custom function in update" issue itself.

## 3. Correct verification behavior
A careful engineer should:
- Define a model with a JSON (or other) field, define a pypika `Function` subclass (e.g. `class JsonSet(Function): def __init__(self, field, expression, value): super().__init__("JSON_SET", field, expression, value)`).
- Create an instance, assign `instance.some_field = JsonSet(F("some_field"), "$.a", 2)`, call `await instance.save()` (optionally with `update_fields=[...]`), then re-fetch the row and confirm the underlying value was transformed by the DB function (not stored as a serialized/bound representation of the Function object, and not raising a binding/type error).
- Also verify `QuerySet.filter(...).update(some_field=JsonSet(...))` produces SQL with the function inlined in the SET clause (e.g. via `.sql()`) rather than as a placeholder parameter, matching the documented example `UPDATE ... SET data_default=JSON_SET(...)`.
- This should work at minimum for SQLite and MySQL (the accompanying test restricts to those dialects via `requireCapability`), confirming `execute_update` correctly special-cases both `ArithmeticExpression` and `Function` instances.
- Separately/additionally, confirm `Model.refresh_from_db(fields=...)` correctly reloads a field previously set to an `F` expression and saved, so the in-memory instance reflects the DB-computed value rather than the leftover expression object; check both scoped (`fields=[...]`) and full refresh.
- Run the existing update/model-method test suite (`tests/test_update.py`, `tests/test_model_methods.py`) against sqlite (and ideally mysql/postgres) to ensure no regression in ordinary value/F-expression updates.

## 4. Traps and near-misses
- Fixing only `execute_update`'s isinstance check but not importing `Function` from `pypika.terms` (or importing from the wrong module) — this silently falls through to attempting to bind the Function object as a parameter, which fails or produces broken SQL depending on driver.
- Treating `Function` values as if they were plain arithmetic expressions and trying to reuse `ArithmeticExpression`-only code paths without widening the isinstance check — a `Function` object is not a subclass of `ArithmeticExpression` in pypika, so a fix that only touches type hints without updating the runtime `isinstance` check does nothing.
- Attempting to solve this purely by adding `refresh_from_db` without touching `execute_update`/`get_update_sql` — this addresses the stale in-memory value problem after save but does not enable custom Function-based updates in `QuerySet.update()`, so the JSON partial-update use case from the issue remains broken.
- Broadening the isinstance check but forgetting to update `get_update_sql`'s parameter/dict naming and usage consistently (e.g. still filtering only on `ArithmeticExpression` keys when deciding whether to bind as parameter vs. use `query.set` directly) would leave `Function` values falling into the parameterized-value branch and failing.
- Confusing this fix with the separate timezone/`DatetimeField` changes bundled in the same release (e.g. `to_python_value`/`to_db_value` awareness handling, `escape_datetime`, MySQL session timezone) — those are unrelated to enabling custom function support in updates and changing them does not verify or fix issue #537; a submission that only touches timezone code without touching `execute_update`/`get_update_sql` does not resolve the reported problem.
- Assuming any callable/expression-like object should bypass parameter binding — the check must remain scoped to `ArithmeticExpression` and `Function` (pypika terms) rather than being loosened to something overly broad (e.g. any non-primitive object), which could break normal value updates for complex field types (JSON dicts, Decimal, etc.) by incorrectly routing them through `query.set` as raw SQL terms.
